# keitaro-campaign-manager

Обёртка над рекламным трекером [Keitaro](https://keitaro.io) с простым веб-интерфейсом:

1. **Создатель кампаний.** Принимает название, гео (коды стран) и ID оффера. Создаёт в Keitaro кампанию с двумя потоками: первый ловит всех из указанных стран и отправляет на Google, второй отправляет трафик на выбранный оффер. Домен, группа и источник трафика берутся из настроек.
2. **Редактор офферов.** Добавляет и удаляет офферы у созданной кампании, пересчитывает доли трафика (всегда поровну, в сумме 100%) и отправляет изменения в Keitaro одним действием.

Стек: Python 3.11+, FastAPI, SQLAlchemy 2.0, Alembic, MySQL 8.4, httpx. Фронтенд: одна HTML-страница без фреймворков.

## Быстрый старт (Docker)

Нужны Docker и Docker Compose.

```bash
cp .env.example .env      # заполните значения (см. раздел «Настройка»)
docker compose up --build
```

При старте контейнер `app` сам применяет миграции (`alembic upgrade head`) и запускает сервер.

- Интерфейс: http://localhost:8000/
- Документация API (Swagger): http://localhost:8000/docs
- Проверка готовности: `curl http://localhost:8000/health` → `{"status":"ok"}`

Остановить: `docker compose down` (данные MySQL сохраняются в томе `db_data`; `docker compose down -v` удалит и их).

## Настройка

Все настройки читаются из переменных окружения; для разработки они лежат в файле `.env` (он в `.gitignore`, секреты в репозиторий не попадают). Образец: `.env.example`.

| Переменная | Что это |
|---|---|
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | Подключение к MySQL. В Docker `DB_HOST` подменяется на имя сервиса `db`. |
| `DB_ROOT_PASSWORD` | Пароль root, нужен только `docker compose` для создания сервера MySQL. |
| `CAMPAIGN_NAME_PREFIX` | Префикс имён кампаний, например `test_ivanov_`. Добавляется автоматически, если его нет в имени. |
| `KEITARO_URL` | Адрес трекера без `/` на конце, например `https://tracker.example.com`. |
| `KEITARO_API_KEY` | Ключ Admin API. |
| `KEITARO_DOMAIN_ID` | ID домена, на котором создаются кампании. |
| `KEITARO_GROUP_ID` | ID группы кампаний. |
| `KEITARO_TRAFFIC_SOURCE_ID` | ID источника трафика. |

Если порт 3306 на вашей машине занят, поменяйте `DB_PORT` в `.env`.

### Где взять ID домена, группы и источника

Через Admin API (ключ передаётся в заголовке `Api-Key`):

```bash
export KEITARO_URL="https://tracker.example.com"
read -s KEITARO_API_KEY && export KEITARO_API_KEY      # ввод не попадает в историю команд

curl -s -H "Api-Key: $KEITARO_API_KEY" "$KEITARO_URL/admin_api/v1/domains"
curl -s -H "Api-Key: $KEITARO_API_KEY" "$KEITARO_URL/admin_api/v1/groups?type=campaigns"
curl -s -H "Api-Key: $KEITARO_API_KEY" "$KEITARO_URL/admin_api/v1/traffic_sources"
```

В каждом ответе нужное поле `id`.

## Как пользоваться интерфейсом

Откройте http://localhost:8000/. Страница состоит из двух вкладок.

### Create campaign

1. **Name**: название. Префикс из `CAMPAIGN_NAME_PREFIX` добавится сам.
2. **Geo**: коды стран через запятую, например `MX,AU,RO`. Допускается и один код.
3. **Offer**: начните вводить название или ID оффера и выберите его из списка. Можно просто ввести числовой ID.
4. Нажмите **Create**. Внизу появится результат (имя кампании, ID в Keitaro, статус) или понятная ошибка.

В Keitaro появится кампания с ротацией «по позиции» и двумя потоками: `Google (<страны>)` (редирект на Google, фильтр «страны: принимать») и `Offers` (выбранный оффер, 100%).

### Edit offers

Вкладка работает с кампаниями, созданными через этот сервис (чужие кампании на общем трекере не затрагиваются). Изменения сначала копятся в **черновике** и уходят в Keitaro только по кнопке:

- **Add offer**: добавить оффер (поиск по названию или ID). Новая строка подсвечивается, доли пересчитываются на экране.
- **Remove**: убрать оффер. Если он уже в Keitaro, строка остаётся серой и зачёркнутой с долей 0% и кнопкой **Bring back**, чтобы вернуть. Если оффер добавлен только что и ещё не отправлен, строка просто исчезает.
- **Push to Keitaro**: отправить весь черновик одним запросом. После ответа таблица показывает реальные данные из Keitaro.
- **Cancel**: отбросить черновик и вернуть состояние Keitaro.
- **Fetch from Keitaro**: заново прочитать кампанию (на случай, если её изменили в самом Keitaro). При несохранённых изменениях спросит подтверждение.

Доли всегда делятся поровну, остаток раздаётся по одному проценту первым офферам: 1 оффер → 100; 2 → 50/50; 3 → 34/33/33; 4 → 25/25/25/25. Пока в черновике нет правок, таблица показывает реальные доли из Keitaro, даже если их выставили вручную другими.

## API

Интерфейс общается с сервисом по этому же API; полная документация и «Try it out» на `/docs`.

| Метод и путь | Что делает |
|---|---|
| `GET /health` | Готовность: `200`, если база доступна, иначе `503`. |
| `POST /campaigns` | Создать кампанию. Тело: `{"name": "au_mx", "geo": "AU,MX", "offer_id": 18813}`. |
| `GET /campaigns` | Список кампаний, созданных через сервис (новые первыми). |
| `GET /campaigns/{id}/offers` | Офферы кампании с названиями и долями, прочитанные из Keitaro. |
| `PUT /campaigns/{id}/offers` | Применить черновик: `{"offer_ids": [1, 2, 3]}`, кампания получит ровно эти офферы (в этом порядке), доли пересчитываются. Пустой список допустим. |
| `POST /campaigns/{id}/offers` | Добавить один оффер: `{"offer_id": 5}`. |
| `DELETE /campaigns/{id}/offers/{offer_id}` | Убрать один оффер. |
| `GET /offers?query=...` | Поиск офферов Keitaro по названию или началу ID (для подсказок). |

Здесь `{id}` это **ID кампании в нашей базе** (поле `id` из `GET /campaigns`), а не ID в Keitaro.

Ошибки приходят в виде `{"detail": "понятное сообщение"}`:

| Код | Когда |
|---|---|
| `404` | кампании или оффера в ней нет |
| `409` | оффер уже в кампании; кампания не активна или в ней нет потока с офферами |
| `422` | некорректные данные: пустое имя, неверные коды стран, ID оффера не положительный |
| `502` | Keitaro вернул ошибку или недоступен (в тексте исходный ответ Keitaro) |

## Как создаётся кампания

1. Кампания сохраняется в нашей таблице `campaigns` со статусом `pending`. Запись переживёт сбой процесса.
2. Генерируется случайный `alias` (8 символов). Если Keitaro отклонил его как дубликат, генерируется новый (до 3 попыток).
3. В Keitaro создаётся кампания, затем два потока.
4. Кампания помечается `active` и сохраняется ID из Keitaro.
5. При ошибке кампания получает статус `failed` и текст ошибки.

## Миграции

```bash
alembic upgrade head                                  # применить все
alembic downgrade -1                                  # откатить последнюю
alembic revision --autogenerate -m "описание"         # создать новую по изменениям моделей
alembic check                                         # модели и миграции совпадают?
alembic upgrade head --sql                            # показать SQL, не подключаясь к базе
```

В Docker миграции применяются автоматически при старте. Автогенерацию нужно просматривать глазами: Alembic не всегда верно угадывает переименования.

## Тесты и проверки

```bash
python -m pytest
ruff check .
ruff format --check .
mypy
```

Тестам не нужны ни MySQL, ни Keitaro, ни сеть. Что покрыто:

- **Домен**: имя кампании с префиксом, разбор и проверка кодов стран, жизненный цикл кампании (`pending` → `active` / `failed`).
- **Доли офферов**: поровну, сумма всегда 100, остаток первым, добавление, удаление, дубликаты, пустой список.
- **Редактор** (сценарий с подставным Keitaro): добавление, удаление, пакетная замена, поиск, потоки без офферов, состав тела запроса `PUT /streams/{id}`.
- **База**: реестр кампаний на SQLite в памяти.
- **`/health`**: ответ при доступной и при недоступной базе.

Не покрыты автотестами: HTTP-клиент к настоящему Keitaro и фронтенд. Они проверены вручную на тестовом трекере.

## Структура

```
app/
├── constants.py        # все числа, строки и тексты ошибок
├── config.py           # настройки из окружения (.env в разработке)
├── domain/             # правила: кампания, гео, доли офферов; чистый Python без I/O
├── application/        # порты (интерфейсы) и сценарии (создание кампании, редактор офферов)
├── adapters/
│   ├── db/             # исходящий адаптер: SQLAlchemy и MySQL
│   ├── keitaro/        # исходящий адаптер: HTTP-клиент Keitaro Admin API (httpx)
│   └── api/            # входящий адаптер: FastAPI
├── static/index.html   # фронтенд
└── main.py             # composition root: связывает всё воедино
alembic/                # миграции
tests/
```

Зависимости направлены внутрь: адаптеры знают о ядре, ядро об адаптерах не знает. Поэтому сценарии тестируются на подставных реализациях портов.

## Принятые решения

- **MySQL и PyMySQL.** Драйвер на чистом Python, ему не нужны системные библиотеки. Пакет `cryptography` нужен для аутентификации MySQL 8.
- **Синхронный стек.** Обычные `def`-эндпоинты, синхронные SQLAlchemy и httpx: вызовов немного, `async` добавил бы сложности без выигрыша.
- **Источник правды о содержимом кампании это Keitaro.** Локальная таблица `campaigns` это реестр: что мы создали и на каком этапе. Редактор перед каждым ответом заново читает потоки из Keitaro, поэтому цифры на экране совпадают с трекером.
- **Редактор работает только с нашими кампаниями.** Трекер общий, и случайно изменить чужую кампанию нельзя.
- **Доли делятся поровну**: правило простое, предсказуемое и одинаково реализовано на сервере (источник истины) и в браузере (для предпросмотра черновика).
- **Тело `PUT /streams/{id}`** собирается по белому списку полей из документации Keitaro: ответ `GET` содержит лишнее (идентификаторы, даты, `null`), которое `PUT` не принимает.
- **Без магических чисел и строк.** Всё вынесено в `constants.py` и сгруппировано по темам; это проверяет `ruff` (правило `PLR2004`).
- **Секреты только из окружения.** `.env` не попадает в Git.

## Ограничения и что улучшить

- **Откат при сбое создания.** Если кампания в Keitaro создана, а потоки создать не удалось, пустая кампания остаётся в Keitaro (у нас запись получает статус `failed`). Следующий шаг: удалять такую кампанию в Keitaro автоматически.
- **Черновик редактора хранится в браузере** и пропадает при перезагрузке страницы. При наличии времени я бы сохранял его на сервере (поле `draft_offers` типа JSON в таблице `campaigns`, отдельная миграция и методы сохранения, отправки и отмены), чтобы он переживал перезагрузку. Keitaro остаётся единственным источником правды, а черновик хранит лишь намерение пользователя.
- **Удаление последнего оффера разрешено.** На тестовом трекере доступен только один оффер, и без этого его нельзя было бы вернуть. Поток при этом остаётся пустым, и трафик из него никуда не уходит. В боевой версии такую операцию стоило бы запретить или требовать подтверждения.
- **Одновременные правки.** Если кампанию изменили в самом Keitaro, пока открыт черновик, отправка перезапишет её содержимое. Защита: кнопка **Fetch from Keitaro** и повторное чтение перед каждым ответом. Блокировок и сравнения версий нет.
- **Поиск офферов** на каждый запрос читает список из Keitaro (для числового запроса сначала ищет точный ID одним запросом). Для большого каталога понадобится кэш или серверная пагинация.
- **Коды стран** проверяются по формату (две латинские буквы), а не по справочнику ISO 3166.
- **Аутентификации нет.** Сервис задуман как внутренний инструмент; наружу его выставлять нельзя: любой, кто до него дотянется, действует с правами ключа Keitaro.
- **Автотестов на HTTP-клиент и фронтенд нет** (см. раздел про тесты).
